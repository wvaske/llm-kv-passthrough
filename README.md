# KV-Bench

**Exercise a real KV manager and storage system with a configurable LLM query
workload, without running model inference.**

Version 1 focuses on workload sensitivity: changing prompt length, completion
length, session history, turns, prefix reuse, or concurrency should produce
credible changes in storage I/O generated by **real LMCache** or **SGLang's
HiCacheFile backend**. It does not
claim that an individual run matches vLLM, SGLang, or TensorRT-LLM performance.

## Fidelity levels

| Level | Scope | Status |
|---|---|---|
| 1 | Explicit prefill/decode rates, naive shared scheduler, rank-aware KV bytes, real LMCache | Implemented |
| 2 | Coupled hardware costs, realistic scheduling/batching/memory pressure | Future work; older analytical utilities are experimental |
| 3 | Chakra-style trace replay with emulated compute and real KV steps | Future extension |

HiCacheFile support uses pinned SGLang v0.5.21 storage code with a modeled V1
host tier; it does not run SGLang's GPU scheduler or HiRadixTree. See the
[HiCache integration contract](docs/architecture/hicache.md) for supported
MHA/GQA layouts, write policies and the CPU-only installation.

Architect's intent, decisions, deferred questions, and acceptance criteria:
[V1 plan](docs/V1_PLAN.md).

## Install and run

Python **3.11+** on Linux. Install from this repository:

```bash
python -m pip install -e '.[lmcache]'
kvbench serve --config examples/rate-v1.yaml
```

The supported integration is pinned to **LMCache 0.5.4**, classic synchronous
engine API. Torch/LMCache are optional for offline tools but required to serve.
No model weights are downloaded and no inference kernels execute.
The CLI hides accelerator devices before loading LMCache, so running on a GPU
host still exercises the CPU adapter. Embedded/direct-uvicorn deployments must
hide accelerators before importing Torch/LMCache; an already selected non-CPU
platform is rejected rather than allocating emulated ranks on real GPUs.

For a quick CPU-tier-only run:

```bash
kvbench serve --model llama-3.2-1b --prefill-tps 10000 --decode-tps 1000
```

The rates above are **illustrative inputs**, not measured guarantees for a GPU.
Rates apply to the entire simulated engine/rank group, not to each request or
rank. Increasing concurrency shares the rates rather than multiplying capacity.

## Configuration

```yaml
server:
  model_profile: llama-3.2-1b
  server_type: combined
  workers: 1
gpu:
  gpu_profile: GB10             # Descriptive hardware profile; rates are authoritative
  tp_size: 1
timing:
  pp_size: 1
  chars_per_token: 4.0         # Synthetic UTF-8 bytes/token, not a real tokenizer
  full_speed: false
scheduler:
  prefill_tokens_per_second: 10000
  decode_tokens_per_second: 1000
  prefill_chunk_tokens: 256
  max_active_requests: 16
  max_pending_requests: 64
  max_context_tokens: 131072
  max_output_tokens: 4096
  request_timeout_s: 600
kv:
  lmcache_config_file: lmcache.yaml
  max_cpu_memory_gb: 2         # Aggregate LMCache CPU-pool safety guard, GiB
  max_chunk_mb: 256           # Maximum rank-chunk payload, MiB
  trace_file: trace.jsonl
```

LMCache's separate file controls storage:

```yaml
chunk_size: 256
local_cpu: true
max_local_cpu_size: 0.25      # GiB PER RANK
local_disk: "file:///tmp/kvbench-cache/"
max_local_disk_size: 0.5     # GiB PER RANK; directory must be on the device under test
```

Paths in a KV-Bench YAML file resolve relative to that file. Explicit CLI
flags override the selected YAML base; without `--config`, the base comes from
`KVBENCH_*` environment variables. File and environment bases are not merged.
Unknown fields fail validation. See the [configuration reference](docs/getting-started/configuration.md).

### GPU and model catalogs are files

The [researched model catalog](docs/architecture/model-catalog.md) includes
DeepSeek V4.1/V4, Qwen3.8, GLM-5.3 and Kimi K3/Linear, with pinned upstream
sources and explicit KV formats. Cache components distinguish growing KV and
indexers from bounded windows and fixed recurrent state. Only growing payloads
are offloaded by V1; the other state is reported separately.

Bundled definitions: `src/kvbench/core/profiles/catalog.yaml`.
Set `profiles_file: my-profiles.yaml` (or `--profiles`) to add/override entries
for one run. Definitions are validated and do not mutate a global registry.
See [custom profiles](docs/architecture/gpu-emulation.md).

```bash
kvbench list-profiles
kvbench info --model llama-3.1-8b
```

KV dtype is independent of weight dtype. TP partitions KV heads (or replicates
them when TP exceeds the head count); PP placement follows the profile's layer ownership.
Invalid partitions fail. Each active logical rank has its own LMCache engine and
artifacts. MLA is represented by replicated latent **byte geometry**, not a
native serving-framework layout. Hardware memory admission is a level-2 feature.

### Measure one drive from a larger TP/PP system

Keep the full modeled topology and choose which ranks actually run LMCache:

```bash
# TP=8 geometry and aggregate compute rates; only rank 0 issues storage I/O.
kvbench serve --config examples/tp8-single-drive.yaml

# Measure two ranks (or any nonempty selection of valid rank IDs).
kvbench serve --config examples/tp8-single-drive.yaml --kv-ranks 0,7

# Override the example's selection to run all eight ranks.
kvbench serve --config examples/tp8-single-drive.yaml --kv-ranks all
```

The YAML setting is `kv.active_ranks: [0]`; omission or `null` runs all ranks.
Global IDs are `pp_rank * tp_size + tp_rank`. Selecting rank 7 alone retains
rank 7's identity and TP=8 shard size. Every request still reaches that rank;
prefill/decode rates remain the configured **whole-engine** rates.

For BF16 Llama 3.1 8B at TP=8, each rank writes **16 KiB/token**, or **4 MiB
per 256-token chunk**. One selected rank writes one file per chunk; all eight
write eight files. Point `local_disk` in the LMCache file at the test drive.
CPU/disk sizes are per active rank; inactive ranks allocate no pools or engines.

Manifests, state and metrics distinguish modeled ranks from active ranks.
Byte counters, capacity and warmup cover active ranks only, with no automatic
extrapolation. Cache hits also reflect only those ranks; omitted-rank eviction
or latency is not simulated. See [rank selection](docs/getting-started/configuration.md#selected-rank-execution)
for environment configuration and reporting details.

## Request and storage lifecycle

1. Bound/admit the request; deterministically format and tokenize its history.
2. Look up and pin the cached prefix across every active rank.
3. Retrieve it through real LMCache; verify completion; release pins.
4. Prefill the missing suffix in scheduled slices; submit each newly completed
   KV chunk to LMCache after the corresponding compute slice.
5. Sample synthetic output. Subsequent decode steps compute KV for the previous
   sampled token and store any newly completed chunks.
6. Complete or cancel the request; drain owned operations and release resources.

Only full LMCache chunks are stored. For a cold request with `P` prompt tokens,
`O` output tokens, and chunk size `C`, computed/storable tokens are:

```text
floor((P + O - 1) / C) * C
```

The final sampled token has not yet passed through the model. A later turn can
compute it. Generated text included verbatim in the next conversation reproduces
the synthetic token prefix, allowing reuse of generated KV as well as prompt KV.

Prefill and decode share a FIFO/round-robin compute lane. A ready scheduling
round costs `prefill_tokens / prefill_rate + decode_tokens / decode_rate`.
I/O-blocked requests do not compute ahead; output is backpressured. `full_speed`
skips only compute sleeps, preserving the same lifecycle. Actual throughput can
be lower because KV I/O, hashing, payload generation, and HTTP work are real.

## Benchmarking and observability

### LMCache versus HiCache and NVMe write amplification

The [single-drive comparison runner](docs/benchmarking/drive-waf.md) qualifies
NVMe backing, drive serial, namespaces and occupancy; samples **host and NAND
bytes** throughout each phase; and requires multiple observed drive fills.
It also captures bounded `blktrace` samples to measure LBA write ordering.
The [live campaign dashboard](http://172.16.2.20:3000/d/kvbench-campaign) follows
phase changes automatically and shows progress, ETA, resource use and health.
The [detailed WAF dashboard](http://172.16.2.20:3000/d/kvbench-nvme-waf) shows
interval/run WAF, rates, occupancy, drive fills and telemetry validity.

```bash
# Read-only qualification; fails when the drive is insufficiently occupied.
python -m kvbench.benchmark.drive preflight --target /mnt/work/kvbench \
  --controller /dev/nvme6 --expected-serial 2337448A0113 --sudo

# Run after qualification/preparation (the example is an ABBA endurance test).
python -m kvbench.benchmark.drive compare --config examples/drive-compare.yaml
```

HiCache is an SGLang feature, not a vLLM feature. Longer sequential writes are
a hypothesis to test: its file backend still writes one file per page, and its
default page-first-direct byte order matches classic LMCache's `KV_2LTD`.

Send OpenAI-shaped chat traffic to `/v1/chat/completions`. Both `max_tokens` and
`max_completion_tokens` work. Streaming supports `stream_options.include_usage`
and reports `usage.prompt_tokens_details.cached_tokens`. With AIPerf, use
`--use-server-token-count` to consume these synthetic token counts directly.
The completion length is fixed; finish reason is `length`. Reported usage counts
**synthetic tokens**; client re-tokenization may produce different counts.

```bash
curl http://localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"llama-3.2-1b","messages":[{"role":"user","content":"Hello"}],"max_completion_tokens":32,"stream":true,"stream_options":{"include_usage":true}}'
```

See the [AIPerf/GenAI-Perf guide](docs/benchmarking/genai-perf.md) for workload
design and the tested protocol boundary.

| Endpoint | Meaning |
|---|---|
| `/health`, `/v1/models` | Readiness and configured model |
| `/metrics` | Prometheus counters and observed latency histograms |
| `/stats` | JSON request, timing, scheduler and KV summary |
| `/kvbench/manifest` | Resolved profiles, rates, ranks, dependency versions and LMCache settings |
| `/kvbench/state` | Rank/tier capacities and KV counters |
| `POST/GET/DELETE /kvbench/warmup` | Fill, inspect, cancel cache warmup |

Warmup is excluded from concurrent serving. KV `stored_tokens` counts submissions,
not confirmed durable writes. Inspect physical trace events for actual disk I/O.
TTFT is measured to first content, not the role chunk. Actual token throughput
uses elapsed server uptime rather than summed request durations.

## Supported scope and limitations

- Combined serving, one worker per process. Use independent combined replicas
  for multiple engines. Legacy proxy/prefill/decode modes fail explicitly.
- Real CPU/local-disk LMCache paths are integration-tested. Remote backends are
  supplied by LMCache but are not certified by this repository's test matrix.
- Async/layerwise/PD/controller/device-specific LMCache paths are not V1 modes.
- Synthetic text and one fixed-length completion; no native tool execution,
  multimodal inference, stop-sequence simulation or multiple choices.
- No native vLLM/SGLang/TensorRT scheduler or physical GPU residency model.
- Payloads have deterministic high entropy; there are no prompt-sized source
  buffers. LMCache's final device copy is omitted. Compression of real floating
  tensors is not modeled.
- Trace-to-FIO is an **experimental approximation**, not a faithful replay.

## Safe development and validation

```bash
python -m pip install -e '.[dev,lmcache]'
bash scripts/test-safe.sh tests/
```

The Linux runner caps the test process at **4 GiB virtual memory**, limits malloc
arenas and numerical-library threads, and disables bytecode/cache writes.
It also hides accelerators so the same CPU-only tests work on GPU hosts.
Real integration fixtures use small CPU pools (at most 64 MiB per rank in the
basic tests). A live-server test separately limits its child process to 4 GiB.
The runtime checks aggregate configured CPU allocation before engine creation.
Without explicit LMCache sizing, the CPU tier defaults to 0.25 GiB per rank.
Cyclic GC remains enabled because LMCache shares the HTTP server process.

Tests cover exact byte/chunk invariants, session/output sensitivity, disk reads
after CPU eviction, TP/PP layouts, KV precision, slow retrieval, cancellation,
bounded admission, partial startup, and actual CLI/HTTP/SSE serving.
